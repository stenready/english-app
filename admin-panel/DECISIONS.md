## API

### API-клієнт — звичайний модуль, а не Vue-плагін

- **Чому:** HTTP-клієнту не потрібні ні реактивність, ні екземпляр застосунку. Модуль імпортується будь-де — у сторі, guard'і, helper'і, тестах. Плагін доступний через `inject()` лише всередині компонентів.
- **Ціна:** немає. Плагін виправданий, коли код справді вбудовується у Vue (глобальні компоненти, директиви) — тут цього немає.

### Весь API — один файл `api/index.ts`

- **Чому:** це один сервіс з однією відповідальністю — транспорт і авторизація запитів. Назовні лише `rest`, `graphql`, `restoreSession`.
- **Ціна:** ~180 рядків в одному файлі. Розділимо, коли з'явиться причина (наприклад, GraphQL сильно виросте).

### Один базовий інстанс `ofetch` + функція `request`

- **Чому:** інстанс (`ofetch.create`) задає `baseURL` і в `onRequest` ставить токен і `Accept-Language`. `request` — спільна обробка помилок для REST і GraphQL: оновлення токена при 401 і перетворення помилок на `AppError`.
- **Чому оновлення токена не в хуку `onResponseError`:** хук може виконати код при помилці, але не може повернути результат повторного запиту замість неї.
- **Ціна:** повтор запиту реалізований вручну — кілька рядків.

### API не робить редиректів

- **Чому:** API-шар не повинен знати про роутер. Інакше його не можна використати без роутера, і з'являється ризик циклічних імпортів (`router` → сторінка → стор → `api` → `router`).
- **Ціна:** реакцію на втрату сесії (редирект на логін) робимо окремо — watcher на `isAuthed` у `App.vue`.

## Авторизація

### Refresh-токен — в httpOnly cookie

- **Чому:** JS його не бачить, тож при XSS його не вкрасти. Браузер надсилає cookie лише на `/api/v1/auth/*` (`Path`).
- **Ціна:** потрібні `credentials: 'include'` і CORS з `credentials: true` та конкретним `origin` на сервері.

### Access-токен — у `localStorage`, один на всі вкладки

- **Чому:** спочатку тримали його лише в пам'яті — це безпечніше, але тоді кожне перезавантаження сторінки вимагає refresh, а кілька вкладок одночасно роблять refresh з тією самою cookie. При суворій ротації refresh-токенів сервер вважає це повторним використанням і розлогінює користувача. `localStorage` спільний для вкладок — токен один, перезавантаження не потребує запиту.
- **Ціна:** access-токен доступний скрипту при XSS. Тому він має жити недовго (5–15 хв); refresh-токен при цьому залишається недосяжним.

### Refresh між вкладками — через `navigator.locks`

- **Чому:** коли токен прострочився, усі відкриті вкладки отримують 401 одночасно. Web Locks API гарантує, що refresh робить лише одна вкладка; інші чекають, бачать у сторі новий токен і refresh пропускають. Перевірено в Chromium з трьома вкладками й суворою ротацією — завжди рівно один refresh.
- **Ціна:** працює лише в браузері, на HTTPS або `localhost`; Safari — з 15.4.

### Токеном володіє стор, API працює лише через стор

- **Чому:** одне джерело правди. Стор ініціалізує токен з `localStorage`, `setToken` пише і в стор, і в `localStorage`. Подія `storage` оновлює стор в інших вкладках. API нічого не знає про `localStorage`.
- **Ціна:** API залежить від Pinia — вона має бути підключена до першого запиту (так і є в `main.ts`).

### `skipAuthRefresh` для логіну й виходу

- **Чому:** 401 на логіні означає «неправильний пароль», а не «прострочений токен». Без прапорця API спробувало б оновити токен і повторити логін з тим самим паролем.
- **Ціна:** прапорець треба не забути передати.

## Помилки

### Одна помилка на весь застосунок — `AppError`

- **Чому:** з API приходять різні помилки: HTTP (`FetchError`), мережа, GraphQL (`errors` з HTTP 200), неочікувані. Фронт отримує їх в одному вигляді: `message`, `code`, `statusCode`, `details`. Формат збігається з помилками сервера (`{ error: { message, details } }`).
- **`code` поруч із `statusCode`:** у мережевої помилки, помилки GraphQL і помилки клієнта `statusCode` однаковий — `null`. `code` (`NETWORK`, `GRAPHQL`…) їх розрізняє.
- **`AppError.from()` проти `new AppError()`:** `from` — коли помилка вже є і її треба привести до нашого вигляду; `new` — коли помилки не було (GraphQL відповів 200, але з `errors`).
- **Ціна:** оригінальна помилка ховається в `cause` — для налагодження треба дивитися туди.

## Роутинг і layout'и

### Layout — через `meta.layout`, а не вкладені роути

- **Чому:** layout обирається для кожного роуту незалежно від розділу, а розділи вже поділені на `public` / `secure`. Вкладені роути групували б за layout'ом і конфліктували б із цим поділом.
- **Ціна:** мапа layout'ів у `App.vue`. `Record<LayoutName, Component>` не дасть забути підключити новий layout.

### Застосунок монтується після `router.isReady()`

- **Чому:** до першої навігації `route.meta` порожній — на мить показався б layout за замовчуванням.
- **Ціна:** немає.

## Компоненти

### Сторінка — `index.vue` у папці `-page` + `defineOptions({ name })`

- **Чому:** папка — це модуль сторінки, поруч можуть лежати її файли. Ім'я компонента Vue бере з імені файлу — для `index.vue` це було б `index` у всіх сторінок, тому ім'я задаємо явно.
- **`PAGE_NAME` / `COMPONENT_NAME` + `data-*-name`:** одна константа для Devtools і для DOM — ім'я не розходиться.
- **Ціна:** два рядки в кожній сторінці й компоненті.

## TypeScript

### Константи — `as const` + виведений тип

```ts
const layoutNames = { AUTH: 'auth', DASHBOARD: 'dashboard' } as const
export type LayoutName = (typeof layoutNames)[keyof typeof layoutNames]
```

- **Чому:** одне місце для значень і типу. Помилка в назві (`'dashbord'`) — помилка типів, а не баг у рантаймі.
- **Ціна:** синтаксис типу незвичний на початку.

### Типізований `route.meta` через `declare module 'vue-router'`

- **Чому:** `layout`, `permissions`, `isPrivate` перевіряються в кожному роуті. Невідомий пермішен — помилка типів.
- **Ціна:** немає.

### Три `tsconfig`

- **Чому:** код застосунку (браузер: `DOM`) і конфіги (`vite.config.ts` тощо: Node) — різні середовища. В одному конфігу типи Node потрапили б у код застосунку (`process`, `Buffer` без помилок, `setTimeout` повертав би `NodeJS.Timeout`). Кореневий `tsconfig.json` лише посилається на обидва — його шукає IDE.
- **Ціна:** три файли замість одного.

## Локалізація

### Тільки пласкі ключі, еталон — `en.json`

- **Чому:** ключ шукається в коді повнотекстовим пошуком одним рядком (`users.list.title`). Тип повідомлень виводиться з `en.json` — якщо в іншій мові бракує ключа, `typecheck` падає.
- **Ціна:** довгі ключі з повторюваними префіксами.

### `Accept-Language` — з поточної мови i18n

- **Чому:** сервер отримує мову користувача в кожному запиті й може повертати тексти помилок нею.
- **Ціна:** немає.
